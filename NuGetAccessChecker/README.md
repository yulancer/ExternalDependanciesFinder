# NuGetAccessChecker

`NuGetAccessChecker` — консольная утилита для проверки доступности NuGet-пакетов из проекта внутри закрытого контура.

Утилита берёт список пакетов и конкретных версий из `.NET`-проекта, затем пытается скачать каждый `.nupkg` из включённых NuGet-источников, доступных для этого проекта через `NuGet.config`. По итогам формируется текстовый отчёт: какие пакеты доступны, из какого источника они были найдены, какие недоступны и какие ошибки возникли по каждому источнику.

## Для чего нужна утилита

Типовой сценарий: проект собирается во внешнем контуре, но затем должен собираться во внутреннем закрытом контуре, где доступен только корпоративный NuGet-feed, например `MyCompany NuGet`.

Перед переносом проекта можно запустить `NuGetAccessChecker` и проверить:

- есть ли все нужные пакеты во внутренних источниках;
- доступны ли конкретные версии пакетов;
- из какого источника берётся каждый пакет;
- какие пакеты нужно заранее загрузить, проксировать или опубликовать во внутренний feed;
- есть ли проблемы с `NuGet.config`, авторизацией, сетью или недоступными URL.

## Что проверяется

Утилита проверяет не просто наличие `PackageReference`, а доступность конкретной пары:

```text
PackageId + Version
```

Например:

```text
Newtonsoft.Json 13.0.3
Serilog 3.1.1
MyCompany.Common 1.2.0
```

Пакет считается доступным, если хотя бы из одного включённого NuGet-источника удалось скачать `.nupkg` нужной версии.

## Как работает алгоритм

Общий порядок работы:

1. Утилита принимает путь к `.csproj` или к папке с `.csproj`.
2. Если передана папка, в ней ищется первый `.csproj` на верхнем уровне.
3. Определяется папка проекта.
4. Собирается список пакетов и версий.
5. Загружаются включённые источники NuGet через стандартные настройки NuGet.
6. Для каждого пакета утилита последовательно проверяет источники.
7. При первом успешном скачивании `.nupkg` пакет считается доступным.
8. Если пакет не найден ни в одном источнике или по всем источникам произошли ошибки, он попадает в раздел недоступных.
9. В конце создаётся текстовый отчёт.

## Источник списка пакетов

Утилита использует два режима получения пакетов.

### 1. Приоритетный режим: `packages.lock.json`

Если рядом с проектом есть файл:

```text
packages.lock.json
```

утилита сначала пытается прочитать зависимости из него.

Это предпочтительный вариант, потому что lock-файл содержит уже разрешённые версии пакетов, включая транзитивные зависимости.

Из `packages.lock.json` читаются элементы из секции `targets`. Ключи вида:

```text
Newtonsoft.Json/13.0.3
```

разбираются как:

```text
PackageId = Newtonsoft.Json
Version   = 13.0.3
```

Если ключ не содержит версию через `/`, утилита пытается взять версию из свойства `resolved`.

### 2. Fallback-режим: `.csproj` + `Directory.Packages.props`

Если `packages.lock.json` отсутствует или не удалось получить из него зависимости, утилита читает `.csproj`.

Поддерживаются версии из:

```xml
<PackageReference Include="Newtonsoft.Json" Version="13.0.3" />
```

```xml
<PackageReference Include="Newtonsoft.Json">
  <Version>13.0.3</Version>
</PackageReference>
```

```xml
<PackageReference Include="Newtonsoft.Json" VersionOverride="13.0.3" />
```

Если версия не указана в `.csproj`, утилита ищет `Directory.Packages.props` вверх по дереву каталогов от папки проекта и читает оттуда:

```xml
<PackageVersion Include="Newtonsoft.Json" Version="13.0.3" />
```

Важно: fallback-режим по `.csproj` и `Directory.Packages.props` обычно видит прямые зависимости. Для проверки транзитивных зависимостей лучше использовать `packages.lock.json`.

## Откуда берутся NuGet-источники

Источники загружаются стандартным механизмом NuGet:

```csharp
Settings.LoadDefaultSettings(projectDir)
PackageSourceProvider(settings).LoadPackageSources()
```

Это значит, что учитываются обычные `NuGet.config`, доступные для проекта и пользователя.

Обычно NuGet берёт настройки из нескольких уровней:

- `NuGet.config` рядом с решением или проектом;
- родительские `NuGet.config`;
- пользовательский NuGet-конфиг;
- машинные настройки NuGet.

Проверяются только включённые источники:

```csharp
.Where(s => s.IsEnabled)
```

Если включённых источников нет, утилита завершает работу с сообщением:

```text
Включённых источников NuGet не найдено. Проверьте NuGet.config.
```

## Как выполняется проверка пакета

Для каждого пакета и версии утилита перебирает все включённые источники NuGet.

Для источника создаётся V3-репозиторий:

```csharp
Repository.Factory.GetCoreV3(src.Source)
```

Затем получается ресурс:

```csharp
FindPackageByIdResource
```

После этого выполняется попытка скачать `.nupkg` в память:

```csharp
CopyNupkgToStreamAsync(...)
```

На каждый источник установлен таймаут 30 секунд.

Пакет считается доступным, если:

- `CopyNupkgToStreamAsync` вернул `true`;
- поток `.nupkg` не пустой.

После первого успешного источника дальнейшая проверка этого пакета прекращается.

## Аргументы командной строки

### Общий вид

```bash
dotnet run -- --project <path-to-csproj-or-folder> [--output <output-file>]
```

### `--project`

Обязательный параметр.

Путь к `.csproj` или к папке, в которой лежит `.csproj`.

Пример с прямым путём к проекту:

```bash
dotnet run -- --project "C:\Projects\MyService\src\MyService\MyService.csproj"
```

Пример с папкой проекта:

```bash
dotnet run -- --project "C:\Projects\MyService\src\MyService"
```

Если передана папка, утилита ищет первый `.csproj` только на верхнем уровне этой папки. Рекурсивный поиск проектов не выполняется.

### `--output`

Необязательный параметр.

Путь к итоговому отчёту.

Пример:

```bash
dotnet run -- --project "C:\Projects\MyService\src\MyService" --output "C:\Temp\nuget-access-report.txt"
```

Если параметр не указан, отчёт создаётся рядом с проектом:

```text
unavailable-packages.txt
```

Отчёт содержит не только недоступные пакеты, но и статистику, доступные пакеты, источники и подробности ошибок.

## Пример `NuGet.config`

Пример конфигурации для закрытого контура:

```xml
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <packageSources>
    <clear />
    <add key="MyCompany NuGet" value="https://nuget.mycompany.local/v3/index.json" />
  </packageSources>
</configuration>
```

Если нужно проверить, что пакеты доступны только из внутреннего источника, желательно временно оставить в `NuGet.config` только корпоративный feed.

Пример с несколькими источниками:

```xml
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <packageSources>
    <add key="MyCompany NuGet" value="https://nuget.mycompany.local/v3/index.json" />
    <add key="NuGet.org" value="https://api.nuget.org/v3/index.json" />
  </packageSources>
</configuration>
```

В таком режиме пакет будет считаться доступным, если он найден хотя бы в одном из включённых источников.

## Формат отчёта

Отчёт создаётся в текстовом виде.

Структура отчёта:

```text
ПРОЕКТ: C:\Projects\MyService\src\MyService\MyService.csproj
ДАТА: 2026-05-05 13:20:00

СТАТИСТИКА:
  Всего проверено: 42
  Доступно:        40
  Недоступно:      2

ПОПАДАНИЯ ПО ИСТОЧНИКАМ:
  MyCompany NuGet: 40

ДОСТУПНЫЕ ПАКЕТЫ И ИСТОЧНИК:
 - Newtonsoft.Json 13.0.3  ->  MyCompany NuGet (https://nuget.mycompany.local/v3/index.json)
 - Serilog 3.1.1  ->  MyCompany NuGet (https://nuget.mycompany.local/v3/index.json)

НЕДОСТУПНЫЕ ПАКЕТЫ:
 - Some.Package 1.0.0
 - Another.Package 2.3.4

ДЕТАЛИ ПО ИСТОЧНИКАМ ДЛЯ НЕДОСТУПНЫХ:
Some.Package 1.0.0
  [MyCompany NuGet] not found (404?)
Another.Package 2.3.4
  [MyCompany NuGet] ERROR: FatalProtocolException - ...
```

## Разделы отчёта

### `ПРОЕКТ`

Полный путь к проверяемому `.csproj`.

### `ДАТА`

Дата и время формирования отчёта.

### `СТАТИСТИКА`

Сводка по количеству проверенных пакетов:

- `Всего проверено` — количество уникальных пар `PackageId + Version`;
- `Доступно` — найдено хотя бы в одном источнике;
- `Недоступно` — не найдено ни в одном источнике или не удалось скачать.

### `ПОПАДАНИЯ ПО ИСТОЧНИКАМ`

Показывает, сколько пакетов было успешно найдено в каждом источнике.

Если подключено несколько источников, раздел помогает понять, откуда реально берутся зависимости.

### `ДОСТУПНЫЕ ПАКЕТЫ И ИСТОЧНИК`

Список доступных пакетов с конкретным источником, где пакет был найден первым.

Формат:

```text
PackageId Version -> SourceName (SourceUrl)
```

### `НЕДОСТУПНЫЕ ПАКЕТЫ`

Краткий список пакетов, которые не удалось скачать ни из одного включённого источника.

Именно этот раздел обычно нужен для подготовки внутреннего NuGet-feed.

### `ДЕТАЛИ ПО ИСТОЧНИКАМ ДЛЯ НЕДОСТУПНЫХ`

Подробная диагностика по каждому недоступному пакету и каждому источнику.

Возможные варианты:

```text
[MyCompany NuGet] not found (404?)
```

Пакет не найден в источнике или источник вернул признак отсутствия пакета.

```text
[MyCompany NuGet] ERROR: FatalProtocolException - ...
```

При обращении к источнику произошла ошибка NuGet-протокола.

```text
[MyCompany NuGet] ERROR: TaskCanceledException - ...
```

Источник не ответил за 30 секунд или операция была отменена по таймауту.

```text
[MyCompany NuGet] ERROR: HttpRequestException - ...
```

Проблема с HTTP-доступом, DNS, сертификатом, прокси или сетевой связностью.

## Требования к проекту утилиты

В проекте `NuGetAccessChecker` должны быть подключены NuGet-библиотеки, которые используются в `Program.cs`:

```xml
<ItemGroup>
  <PackageReference Include="NuGet.Protocol" Version="6.12.1" />
  <PackageReference Include="NuGet.Configuration" Version="6.12.1" />
  <PackageReference Include="NuGet.Versioning" Version="6.12.1" />
</ItemGroup>
```

Версии можно заменить на те, которые приняты в вашем проекте. Главное, чтобы API были совместимы с используемым кодом.

В коде есть комментарий про NuGet `4.3.1`: для этой версии в `Repository.Factory.GetCoreV3` передаётся строка URL, а не объект `PackageSource`.

## Требования к проверяемому проекту

Для максимально точной проверки желательно:

1. Выполнить restore проекта до запуска проверки.
2. Включить lock-файл, если нужно проверять транзитивные зависимости.
3. Убедиться, что рядом с проектом или выше по дереву лежит корректный `NuGet.config`.
4. Убедиться, что в закрытом контуре доступны нужные сертификаты, прокси и DNS.

## Как включить `packages.lock.json`

Чтобы проект создавал lock-файл, можно добавить в `.csproj`:

```xml
<PropertyGroup>
  <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
</PropertyGroup>
```

После этого выполнить:

```bash
dotnet restore
```

Рядом с проектом появится:

```text
packages.lock.json
```

После появления lock-файла `NuGetAccessChecker` сможет проверять не только прямые, но и транзитивные зависимости.

## Важные ограничения

### Проверяется один проект

Утилита принимает один `.csproj` или одну папку с одним `.csproj` на верхнем уровне.

Она не обходит всё решение рекурсивно и не проверяет сразу все проекты в `.sln`.

### Транзитивные зависимости берутся из lock-файла

Если `packages.lock.json` отсутствует, fallback-режим читает `.csproj` и `Directory.Packages.props`. В этом режиме транзитивные зависимости обычно не будут найдены.

Для проверки полного графа зависимостей используйте lock-файл.

### Условные `PackageReference` могут быть обработаны не полностью

Fallback-чтение `.csproj` выполняется как XML-разбор. Условия MSBuild не вычисляются так же полно, как при настоящем restore.

Например, такие зависимости могут попасть в список без учёта условия:

```xml
<ItemGroup Condition="'$(TargetFramework)' == 'net8.0'">
  <PackageReference Include="Some.Package" Version="1.0.0" />
</ItemGroup>
```

Для точного результата снова лучше использовать `packages.lock.json`.

### Версии с MSBuild-переменными пропускаются

Если версия содержит `$`, она пропускается:

```xml
<PackageReference Include="Some.Package" Version="$(SomePackageVersion)" />
```

Исключение — если версия разрешается через `Directory.Packages.props` и там указано конкретное значение.

### Проверяется скачивание `.nupkg`, а не успешная сборка

Утилита проверяет доступность пакета в источнике. Она не проверяет:

- совместимость пакета с target framework;
- конфликты версий;
- успешность компиляции проекта;
- runtime-ошибки;
- доступность symbol/source packages.

### Первый успешный источник фиксируется в отчёте

Если пакет есть в нескольких источниках, в отчёте будет указан первый источник, из которого удалось скачать пакет.

Порядок источников определяется настройками NuGet.

## Рекомендованный процесс использования

### 1. Подготовить проект

Выполнить restore:

```bash
dotnet restore "C:\Projects\MyService\src\MyService\MyService.csproj"
```

При необходимости включить lock-файл и повторить restore.

### 2. Настроить `NuGet.config`

Для проверки закрытого контура оставить только внутренний источник:

```xml
<packageSources>
  <clear />
  <add key="MyCompany NuGet" value="https://nuget.mycompany.local/v3/index.json" />
</packageSources>
```

### 3. Запустить проверку

```bash
dotnet run -- --project "C:\Projects\MyService\src\MyService" --output "C:\Temp\nuget-access-report.txt"
```

### 4. Проанализировать раздел `НЕДОСТУПНЫЕ ПАКЕТЫ`

Пример:

```text
НЕДОСТУПНЫЕ ПАКЕТЫ:
 - Some.Package 1.0.0
 - Another.Package 2.3.4
```

Эти пакеты нужно добавить во внутренний NuGet-feed, разрешить через proxy/feed-mirroring или заменить в проекте.

### 5. Повторить проверку

После публикации недостающих пакетов повторить запуск и убедиться, что `Недоступно: 0`.

## Типовые проблемы и причины

### `Включённых источников NuGet не найдено`

Причины:

- отсутствует `NuGet.config`;
- все источники отключены;
- утилита запускается не из той папки;
- настройки NuGet не видны из папки проекта.

Что проверить:

```bash
dotnet nuget list source
```

### `not found (404?)`

Пакет или версия отсутствует в источнике.

Что проверить:

- правильность версии;
- наличие пакета во внутреннем feed;
- синхронизацию proxy-feed;
- регистр и точное имя пакета.

### `TaskCanceledException`

Обычно означает таймаут обращения к источнику.

Что проверить:

- доступность NuGet URL;
- прокси;
- VPN;
- DNS;
- firewall;
- производительность внутреннего feed.

### `HttpRequestException`

Чаще всего проблема сетевого уровня.

Что проверить:

- DNS-имя источника;
- сертификаты;
- корпоративный proxy;
- доступность URL из закрытого контура;
- настройки TLS.

### Ошибки авторизации

Если источник требует авторизацию, нужно убедиться, что credentials доступны NuGet-клиенту.

Обычно они настраиваются в `NuGet.config` или через credential provider.

## Кратко

`NuGetAccessChecker` отвечает на вопрос:

> Сможет ли проект восстановить нужные NuGet-пакеты из источников, доступных внутри закрытого контура?

Основной результат работы — отчёт, где видно:

- сколько пакетов проверено;
- какие доступны;
- из какого источника они доступны;
- какие недоступны;
- какая ошибка возникла по каждому источнику.
